# Sticky Stripe Connect v2 checkout

Use this skill for Sticky-managed Stripe payments, campaign/SKU checkout links, or updates to the existing Fly checkout. Read the [application guide](../../../tools/stripe-v2-checkout/README.md) and [Fly deployment guide](../../../tools/stripe-v2-checkout/FLY.md). For catalog exploration or synthetic billing tests, use [stickyio-catalog-billing](../stickyio-catalog-billing/SKILL.md).

## Working implementation

Source: `tools/stripe-v2-checkout`. FastAPI + Stripe.js Elements, persistent SQLite, one Uvicorn worker on one Fly machine. Host: `https://wlmd-stripe-test-0f89b1bb.fly.dev`.

Links follow `/checkout/{campaign_id}/{url_encoded_sku}`. Example: `/checkout/422/WLMD-CORE-2USD-0f89b1bb`. The owner explicitly chose **any campaign/SKU accessible to the Sticky API**, rather than an application allowlist. Keep the existing private invitation/cookie access. A URL alone must not bypass Sticky campaign permissions or permit an arbitrary amount, gateway or PaymentIntent.

Resolve campaign → configured offers → candidate product details → exact SKU → configured billing models. Duplicate SKUs can represent distinct products; show every matching offer/product/model choice. Do not search the whole account or trust previously ignored global SKU filters. Preserve campaign integrations and routing; never send campaign PUTs to make checkout work. Read the campaign's **Stripe Link alternative payment** mapping and confirm provider **250**, then obtain that profile's publishable key and currency. Provider 180 is the older integration. Do not force profile 254 onto unrelated brands.

Standard one-time and day-based self-recurring offers are implemented. Recurring billing requires explicit displayed consent. Campaign countries and shipping choices are enforced. Trial, prepaid, series, seasonal, bundle, variant and custom schedules resolve but remain blocked where their additional selections are unsupported; never silently sell them as a standard one-time product. Delayed/capture-on-shipment profiles and unsupported currencies are blocked. Resolving any accessible SKU does not mean every offer is currently payable in this harness.

## Quote and pay

1. `POST /api/v2/order_total/calculate` with `campaign_id`, campaign `shipping_id` when selected, `use_tax_provider: 1`, billing/shipping `location`, and `offers: [{id: offerId, product_id, billing_model_id, quantity: 1}]`. This endpoint uses offer **id**, unlike new_order's **offer_id**. Do not override price. Require a positive, two-decimal, single-product total; currency comes from the gateway.
2. Store the quote, selection, contact and configuration fingerprint per checkout. Quotes expire after ten minutes; recheck configuration and total before authorization and capture. A changed price or route requires review, not a silent amount substitution.
3. Sticky `POST /api/v1/authorize_payment`: explicit first/last name, billing and shipping address fields, normalized email/phone, `billingSameAsShipping: "YES"`, `creditCardType: "stripe_link"`, `forceGatewayId`, `campaignId`, `productId`, trusted `ipAddress`, and **`auth_amount` in major currency units**. Using `amount` or `productPrice` instead caused HTTP 500 in the initial experiment.
4. Require response code 100, `digitalWalletToken` shaped as a Stripe client secret, and matching `transactionID` or `transId` PaymentIntent prefix. Store the intent ID server-side; keep its client secret only in process memory. Return only the public key and this checkout's secret to the authenticated browser. Card data belongs only in Stripe Elements.
5. Stripe.js confirms that same intent and completes its frontend challenge using the actual HTTPS campaign/SKU return URL. Validate returned intent ID, amount, currency and `requires_capture`. A `succeeded` or uncertain result needs reconciliation; never capture twice.
6. Sticky `POST /api/v1/new_order`: same customer/campaign/gateway, `creditCardType: "stripe_link"`, `tranType: "Capture"`, server-stored `transactionId`, `three_d_redirect_url`, campaign shipping selection, blank PAN/expiry/CVV, and `offers: [{offer_id, product_id, billing_model_id, quantity: 1}]`. Preserve configured pricing by omitting custom price. Do not create an independent Stripe charge followed by an offline order.
7. Require response code 100 and read back `order_view`. Verify approved status, total, campaign, gateway, product, offer, model, quantity and recurring flag before recording completion. Sticky response 101 is currently held for additional API 3DS reconciliation; its completion endpoint is not implemented here. Timeouts and mismatches also hold the attempt. No automatic write retries.

No separate Stripe private key is needed for this Sticky-managed flow. Gateway profiles contain OAuth/access/refresh tokens: never dump raw profiles or extract credentials. A production reconciliation service may need additional processor verification; the current harness relies on Sticky approval/read-back and browser confirmation, and does not independently retrieve PaymentIntents server-side.

## Durable state and hosting

Keep `/data` and its invitation, legacy `purchase` table and new `checkouts` table. The migration preserves the original receipt/uncertain attempt. Campaign/SKU URLs are reusable checkout entry points. Existing attempt cookies retain their receipt; new visitors receive their own fresh attempt, including on the original $2 URL. After completion, the explicit “Start another purchase” action calls POST /api/new-purchase with previous_attempt_id to create a separate attempt and set its secure cookie. Never reset the old row, contact or intent. The purchase_successors table gives each completed attempt at most one successor, so double clicks/replayed requests return the same new attempt. Pending or uncertain payments cannot start a successor. X-Checkout-Attempt pins API requests to the current purchase; stale tabs must reload instead of acting on a new purchase. Repeated capture returns the stored receipt; pending states cannot be reset through the API. One machine/worker is required because secrets are process-local.

Reuse Fly app `wlmd-stripe-test-0f89b1bb`, machine `84e117f290dd38`, volume `vol_40o3gdk37mo7zy24` (`checkout_data`, iad, personal). Do not provision replacements or scale horizontally. Fly already has both Sticky credentials. Cloud bindings are proxy-backed and scoped; do not copy placeholders to Fly or ask for existing secrets again.

Before an authorized deployment, inspect all purchase/checkouts statuses. Reconcile pending attempts before a restart. Run offline tests and JavaScript syntax checks, build with `build_image.py`, verify the image locally, upload with `push_image.py`, and deploy its verified immutable digest with `--ha=false --strategy immediate --yes`. The HTTPS chunked uploader works through the environment's credential proxy; ordinary Docker push failed there. Preserve TLS verification. Use `FLY_CONFIG_DIR=/workspace/scratch/fly-config`, `DOCKER_CONFIG=/workspace/scratch/docker-config` and the securely bound `FLY_API_TOKEN`. Full commands and verification details are in FLY.md.

Check public health, unauthenticated rejection, private page, receipt migration, campaign/SKU config and a read-only pricing calculation after deployment. Do not authorize or capture a new live payment as a health check. Invitation tokens, real contact data, card details, client secrets and gateway tokens must never enter source, reports, logs or this skill. Access logging is disabled; Stripe return query parameters are removed immediately.
